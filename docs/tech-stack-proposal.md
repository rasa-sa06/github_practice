# 技術選定の案

受注管理システム（提案書の②③④）をどう作るかの提案です。**まだ決定ではありません。**
前提は [`admin-system-brief.md`](admin-system-brief.md)、全体像は [`project-map.md`](project-map.md) にあります。

この文書は「何を使うか」だけでなく、**設計ルールのどれがその選択を要求したか**を書いています。
あとで別の技術に差し替えるときも、同じルールを満たすかどうかで判断できるようにするためです。

---

## 結論

| 役割 | 使うもの |
|---|---|
| 画面とサーバー | **Next.js（App Router・TypeScript）** |
| ホスティング | **Vercel**（サイトとは別プロジェクト。同じリポジトリの `admin/` を指す） |
| データベース | **Neon（PostgreSQL）** — Vercel の連携から作成 |
| DBの操作 | **Drizzle ORM** |
| ログイン | **Auth.js（NextAuth）＋ LINEログイン**。使えるアカウントは1つだけに限定 |
| 写真の保管 | **Vercel Blob** |
| 文章生成 | **Claude API（`claude-opus-5`）** |
| LINEの受信 | **LINE Messaging API**（Webhook）— ただし**一番最後に入れる** |
| アプリの見え方 | **PWA**（ホーム画面に置く。アプリストアは使わない） |

追加の月額はほぼ発生しません（後述の「費用」）。
ただし **Vercel の無料プランは商用利用を認めていない可能性が高く**、ここだけ確認が要ります。

## なぜこの構成なのか

技術より先に、設計ルールが決めている部分があります。

### 「再開できる」がデータベースの選択を決めています

> 何日ぶりでも「おかえりなさい」から始まる。空白を指摘しない

これは画面の文言の話に見えて、**インフラの要件**です。
10日ぶりに開いたときにデータベースが止まっていて画面が出ない、というのは
設計ルールの真逆をやることになります。

無料枠のマネージドDBには、**一定期間アクセスがないとプロジェクトごと停止し、
管理画面から手で再開しないと戻らない**タイプのものがあります（Supabase の無料プランがこれに当たります）。
このシステムでは採用できません。

Neon は使われていない間スリープしますが、**接続が来ると自動で起きます**。
手動の操作は要りません。最初の1回だけ1秒ほど待つことがありますが、止まったままにはなりません。

> 料金プランの条件は変わります。**契約前に「無操作でどうなるか」を必ず確認してください。**
> この1点だけは、他の条件より優先して見る価値があります。

### 「押すだけで進む」「数えるのはやったことだけ」がデータの持ち方を決めています

注文に「進捗 5/8」という数字を持たせて上書きしていく作り方は、素直ですが行き止まりです。
④きろく（今月つくったリボン・続いている日数・バッジ）を出そうとした時点で、
「いつ何個できたか」が残っていないことに気づきます。

そこで、**「やったこと」を1行ずつ足していくだけの記録（イベント）**を1つ持ち、
画面はすべてそこから計算して出します。

| 画面 | 何から作るか |
|---|---|
| ②注文のステータス | そのイベントのいちばん新しいもの |
| 注文詳細の「5/8個」 | 「1個できた」の件数 |
| ①きょう | 次に手が要るものを並べ替えただけ |
| ④きろく・バッジ・クエスト | 同じイベントを数え直しただけ |

この形にすると、**④のゲーム要素のための入力が1つも要りません。**
「ゲームのために新しい作業を増やさない」は、頑張って守るものではなく、
データの持ち方で最初から不可能にしておけます。

「1個できた」を押す＝イベントを1行足す、だけです。数値入力も日付選択も発生しません。
書き換えでなく追加なので、**過去に戻って何かを消す動作がありません。**
「止まっていた期間を途切れとして見せない」も、そもそも記録されていないので表示しようがない、という状態になります。

### 「スマホだけで完結」がログイン方法を決めています

メールのマジックリンクは、毎回メールアプリに移動することになります。
パスワードは、久しぶりに開いたときに思い出せないと、そこで止まります。
どちらも「再開できる」を壊します。

**LINEログイン**なら、すでに毎日開いているアプリの中で終わります。
そのうえでセッションを長め（1年）に持たせ、**普段はログイン画面を一度も見ない**状態にします。
ログインできるアカウントは依頼者の LINE ユーザーID 1つだけに限定します（他の人が開いてもログインできません）。

PWA としてホーム画面に置けば、見た目も動きもアプリになります。アプリストアの審査も年会費も要りません。

> **通知は入れない案です。** 技術的には可能ですが、
> 「◯件たまっています」を送る仕組みは「責めない」と正面から衝突します。
> お客様からの連絡の通知は、これまでどおり LINE そのものが出してくれます。

## 未決だった3点への回答

### 1. 同じリポジトリに入れるか、分けるか → **同じリポジトリに入れる**

`admin/` というフォルダを作り、その中だけで完結させます。今のサイトのファイルは1つも触りません。

分けない理由は、`project-map.md` に書かれているとおりです。

> 成果物がリポジトリの外にも散らばっていて、「あれ作ったっけ？」で作業が止まったことが実際にありました。

リポジトリを分けると、この問題をもう一度自分で作ることになります。
資料（提案書・デモ・引き継ぎ）はすべてここに集まっているので、コードも同じ場所が自然です。

**このリポジトリは公開されている点だけ、判断が要ります。**
コードが公開されること自体は問題ありません（パスワードや鍵はコードに書かず Vercel 側に預けるため、
公開されていても他人が入れるようにはなりません）。**お客様の情報はデータベースにだけ入り、リポジトリには一切入りません。**
気になる場合はリポジトリを非公開に変えられます。非公開でもサイトの自動デプロイはそのまま動きます。

### 2. ホスティング → **Vercel のまま。ただし別プロジェクトとして追加**

同じリポジトリから、Vercel のプロジェクトを2つ動かします。

| プロジェクト | 見る場所 | 中身 |
|---|---|---|
| 今あるもの | リポジトリの一番上 | 静的サイト（触りません） |
| 追加するもの | `admin/` | 管理システム |

サイト側の設定は変更しません。**管理システムの作業中にサイトが壊れることがない**のが、この分け方の利点です。

> 補足：Instagram連携が毎朝 `main` にコミットするので、放っておくと
> 毎朝、管理システム側も無駄に再ビルドされます。
> Vercel の「対象フォルダに変更がなければビルドしない」設定を入れておきます。

### 3. どこまで自作するか → **画面と状態遷移だけ。他は全部借りる**

これがこの提案でいちばん大事な線引きです。

| 自分で作る | 借りる（作らない） |
|---|---|
| 4つの画面と、その見せ方 | ログインの仕組み（Auth.js） |
| ステータスの進み方 | データベース本体（Neon） |
| 「何を大きく出すか」の判断 | 写真の保管（Vercel Blob） |
| | 文章の生成（Claude API） |

そして、**年に1回あるかどうかの操作には画面を作りません。**
（例：入力ミスの修正、古いデータの削除）
Neon の管理画面から直接直せます。制作者が対応すれば済むことに画面を用意すると、
使われない画面が増えて、あとで直す対象だけが増えます。

#### スプレッドシートで済ませる案について

`admin-system-brief.md` に挙がっていた案です。結論として、**この用件には向きません。**

ステータスを記録するだけならスプレッドシートで足ります。しかし設計ルールのうち、

- 一手だけ（大きく1つ、あとは薄く）
- 押すだけで進む
- 色は3色
- 責めない

は、**どれもスプレッドシートでは表現できません。**
スマホでスプレッドシートを開くと、まずセルを探すところから始まります。
それは「見れば分かる」ではなく「操作を覚える」に戻ることを意味します。

**この提案の価値は機能ではなく、画面の出し方にあります。**
そこを既製品に置き換えると、残るものがほとんどありません。

## 注文が月に何件でも、この構成は変わりません

`admin-system-brief.md` は「注文が月に何件かを確認せずに作り始めないでください」としています。これは正しい指摘です。

そのうえで補足すると、**件数によって変わるのは「どこまで作るか」であって、「何を使うか」ではありません。**

| 月の件数 | 使う技術 | 作る範囲 |
|---|---|---|
| 0〜2件 | 同じ | フェーズAだけ作って、使われるか見る |
| 3〜10件 | 同じ | この提案どおり |
| 10件以上 | 同じ | 同じ。この構成で困りません |

つまり**技術選定は、件数の答えを待たずに決めて構いません。**
件数の答えが要るのは、フェーズA のあとに進むかどうかの判断のときです。

なお、件数が少ないほど作る意味がない、とは限りません。
提案書が挙げているのは「抜け漏れ・先送り・段取りが苦手」であって、これは**件数ではなく、
覚えておかなければならない状態そのもの**が負担になる話です。1件でも効く可能性はあります。
だからこそ、**まずフェーズAだけ渡して、実際に使われるかを見るのがいちばん確実です。**

## 作る順番

4画面を一度に作りません。**先に②を作ると、①と④はほとんど計算だけで出てきます。**

| | 作るもの | なぜこの順番か |
|---|---|---|
| **A** | ログイン ＋ ②注文一覧 ＋ 注文詳細（「1個できた」・お聞きしていること・LINEをひらく） | ここだけで実際に使える。①④に必要な記録もここで貯まり始める |
| **B** | ①きょう | Aのデータを並べ替えるだけ。新しい入力は増えない |
| **C** | ④きろく | 同じ記録を数え直すだけ。実装量は小さい |
| **D** | ③文章をつくる | 独立している。他と切り離してあとから足せる |
| **E** | LINE Messaging API での自動受信 | 下に理由 |

### なぜ LINE の自動受信を最後にするか

デモの「LINEをひらく」は**リンクを開いているだけ**で、Messaging API は使っていません。
つまり **A〜D は LINE の設定を一切変えずに作れます。**

一方 Messaging API を有効にすると、**いま実際にお客様が使っている公式アカウントの動作**に影響します
（応答モードや自動応答の扱いが変わります）。
まだ使われるか分からない管理画面のために、**動いている窓口に手を入れるのは順番が逆です。**

A〜D が実際に使われていることを確認してから、依頼者のアカウントで一緒に設定するのが安全です。

## 費用

| | 月額 | 備考 |
|---|---|---|
| Vercel | 0円 or 約3,000円 | **下記の確認事項を参照** |
| Neon（DB） | 0円 | 無料枠で十分な規模です |
| Vercel Blob（写真） | 0円 | 同上 |
| LINE公式アカウント | 0円 | 現在のプランのまま。**送信の上限は要確認** |
| Claude API（文章生成） | 数十円〜数百円 | 使った分だけ。月50回生成しても200円程度 |

文章生成には `claude-opus-5` を使う案です（100万トークンあたり入力 $5・出力 $25）。
写真1枚＋これまでの言い回しを読ませて数百字を書く用途で、1回あたり0.1〜0.2円程度です。
**この規模では、安いモデルに落とす理由がありません。**文章の質がそのまま成果物になる部分なので、
上のモデルを使っても月額は誤差の範囲です。

## 確認・注意が要ること

作り始める前に、制作者側で確認します。ここは**まだ確定していない情報**です。

| | 内容 |
|---|---|
| **Vercel の商用利用** | 無料（Hobby）プランは個人の非商用向けとされています。受注管理は事業利用に当たるため、**有料プラン（約$20/月）が必要になる可能性が高い**です。規約を確認します。今のサイト自体も同じ論点を含みます |
| **LINEの送信上限** | 無料プランには月あたりの配信通数の上限があります。返信や手動チャットが上限に含まれるかは料金ページで確認します。フェーズEに進むときの論点で、A〜Dには影響しません |
| **DBの無操作時の挙動** | 上に書いたとおり、契約前に必ず確認します。プランの条件は変わるため、この文書の記述を信用しないでください |
| **Vercel の実行リージョン** | 東京を指定できるかはプランによります。指定できなくても、体感で気になる差にはなりません |

## この案を採用する場合、次にやること

1. 上の「確認・注意が要ること」を制作者が確認する
2. 依頼者に、`admin-system-brief.md` の3つの質問を確認する
   （注文の件数／いま一番困っていること／どこから使い始めたいか）
3. **2の答えでフェーズAの中身を微調整してから**、`admin/` の作成に入る

技術選定そのものは2の答えを待ちません。待つのは、**作る範囲**の決定です。
